# Живые субтитры на русском: варианты и архитектура

Документ-предложение. Дата: 13.10.2026. Составлен по официальным страницам проектов и карточкам моделей (ссылки в конце); замеры на конкретном ноутбуке ещё не делались — это отдельный этап (см. «Этап 0»).

---

## 1. Что требуется

| # | Требование | Следствие для архитектуры |
|---|---|---|
| 1 | Распознавать речь, которую жена слышит **в наушниках** (голоса клиентов из созвона) | Захват системного микса вывода (WASAPI loopback) или, лучше, звука только приложения-конференции (process loopback) |
| 2 | Русский язык | Выбор модели сужается: нужны русскоязычные ASR |
| 3 | Субтитры на **прозрачном фоне** поверх всех окон | Отдельное окно-оверлей: без рамки, click-through, always-on-top, не забирает фокус |
| 4 | Слова появляются **по мере речи**, а не после конца фразы | Нужен потоковый (online) распознаватель с частичными гипотезами, либо скользящее окно с перераспознаванием |
| 5 | Задержка «почти без» — ориентир ≤ 1 с | Бюджет задержки разложен в §5; жёсткая экономия на каждом звене |
| 6 | Локально, офлайн, без облака | Приватность звонков с клиентами; никаких API наружу |
| 7 | Работает на CPU или встроенной графике (Ryzen 7 7840HS, Radeon 780M) | Малые модели (70–250 млн параметров) и/или DirectML/Vulkan; CPU — базовый путь |
| 8 | Быстрое, «скомпилированное» приложение | Язык оболочки: C#/.NET или Rust; ядро ASR всё равно нативный C++ (sherpa-onnx) |

Дополнительно, из практики поддержки (предлагаю заложить в v1):

- **Скрывать субтитры от демонстрации экрана** — иначе клиент увидит «подсказки» на её экране. Технически решается флагом `WDA_EXCLUDEFROMCAPTURE` (§7), но требует проверки на её приложении.
- **Не перехватывать фокус и мышь** — иначе приложение сломает ей работу в день первого запуска.
- **История и экспорт** последних минут в `.txt`/`.srt` — бонус для протокола обращений.
- **Транскрибировать и её реплики** (микрофон) — опционально, отдельным каналом с пометкой «Вы:».

Требование «как в Windows Live Captions, но по-русски» технически понятно: встроенная функция не поддерживает русский, поэтому нужен собственный движок.

## 2. Главный вывод (TL;DR)

**Ничего с нуля обучать не нужно.** Уже существуют: (а) открытая русская **потоковая** ASR-модель, (б) нативный Windows-движок, который её запускает, (в) готовые системные API для захвата звука и оверлея. Остаётся написать «оболочку» из трёх частей:

```
наушники/колонки ──► захват вывода (WASAPI) ──► ASR-стриминг ──► прозрачный оверлей
      (что слышит жена)     16 кГц, моно        T-one CTC        субтитры
```

Рекомендуемая база — **`sherpa-onnx-streaming-t-one-russian-2025-09-08`**: русская потоковая модель T-one (Т-Банк, 71 млн параметров, Apache 2.0), сконвертированная в ONNX и поддержанная в движке sherpa-onnx как штатный online-режим (`t_one_ctc`). Это настоящий стриминг чанками по 300 мс — слова выводятся по мере поступления аудио, ровно то поведение, которое нужно. Модель весит 138 МБ, работает на CPU, лицензия Apache 2.0 позволяет любое использование.

Оболочку предлагаю писать на **C#/.NET 8** (быстрее всего до рабочего результата, есть биндинги sherpa-onnx, NAudio для захвата, WPF для оверлея) либо на **Rust** (компактный один exe, крейты `wasapi` + `windows` + биндинги sherpa-onnx) — сравнение в §6. Python использовать только для этапа замеров.

Примечания к таблице:

1. **Строки T-one/Vosk/Whisper/GigaAM-v2** взяты из одной таблицы — из README T-one: все четыре модели прогнаны на одних и тех же наборах (колл-центр, телефония, имена сущностей, CommonVoice 19, OpenSTT). Сам факт единого набора делает эти числа сопоставимыми.
2. **GigaAM-v3** сравнивается в собственной карточке на HF с «T-One + LM» и Whisper, но на своих доменах; по этой таблице GigaAM-v3 точнее T-one (среднее 8.4–9.2 против 19.4 у T-one с языковой моделью). Обе таблицы — заявления вендоров. Практический вывод: **T-one — для мгновенного вывода, GigaAM-v3 — для уточнения/архива**, и окончательный выбор делается замером на реальных записях (Этап 0).
3. **GigaAM-v3** выпущен в вариантах `ctc`, `rnnt`, `e2e_ctc`, `e2e_rnnt` (последние два добавляют пунктуацию и нормализацию текста) — карточка модели; для sherpa-onnx есть готовые конвертации (в т.ч. от сборщика моделей k2-fsa).
4. **T-one** обучен в первую очередь на телефонии (80 000 часов русской речи, из них телефония — 57.9 тыс. часов), и по README «устойчив и вне домена телефонии». Для работы в поддержке, где голос идёт через VoIP-кодек, это попадание в целевой домен, а не компромисс.
5. **Ограничение T-one по частоте**: конвертированная модель ожидает 8 кГц, движок сам ресемплит вход. Для широкополосного созвона это означает потерю части спектра, но с учётом телефонийного обучения модели такое понижение качества ожидаемо терпимо — проверяется на Этапе 0.
6. Про **GigaAM-v3 скорость**: сторонний проект-расшифровщик на GigaAM-v3 + sherpa-onnx для Windows заявляет обработку «в ~30 раз быстрее реального времени» (1 час записи ≈ 2 минуты). Если это подтвердится на её ноутбуке, скользящее окно 1.5–2 с с перераспознаванием каждые 200–300 мс даёт задержку ~0.8 с при почти «офлайн» качестве. Это и есть обоснование двухступенчатой схемы.
7. **Whisper-семейство** исключено из роли ядра: на 8 ядрах Zen4 модели `small` уступают по качеству русскому T-one, а `large-v3`/`turbo` не успевают в реальном времени без GPU. Остаётся как офлайн-инструмент для точной расшифровки сохранённых записей.

**Итоговая рекомендация:** v1 — T-one streaming; v2 — добавить GigaAM-v3 как «вторую ступень» (см. §5.3). Vosk — страховка на случай проблем с T-one (например, если понадобится русский стриминг с более щадящими требованиями к ресурсам).

## 4. Архитектура

### 4.1 Поток данных

```
 ┌─────────────────────────────────────────────────────────────────────┐
 │ 1. Захват звука (аудио-поток)                                       │
 │   • WASAPI loopback устройства вывода по умолчанию → слышим клиента │
 │   • опционально WASAPI process loopback → только аудио приложения   │
 │     созвона (Teams/Zoom/браузер), без музыки и уведомлений          │
 │   • опционально микрофон → транскрипт её собственных реплик         │
 │   Буфер 20–40 мс, ресемплинг 48k → 16k моно (движок ресемплит в 8k) │
 └───────────────────────────┬─────────────────────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ 2. Подготовка и сегментация                                         │
 │   • кольцевой буфер (без аллокаций в аудио-колбэке)                 │
 │   • VAD (Silero, встроен в sherpa-onnx) → гейт тишины и эндпоинты   │
 │   • chанки ровно по 300 мс для T-one                                │
 └───────────────────────────┬─────────────────────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ 3. Распознавание: sherpa-onnx, online-режим (t_one_ctc)             │
 │   • model.onnx (138 МБ) + tokens.txt, ONNX Runtime CPU, 4–6 потоков │
 │   • на каждые 300 мс — обновлённая гипотеза (текст + таймкоды)      │
 └───────────────────────────┬─────────────────────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ 4. Стабилизатор текста                                              │
 │   • подтверждённый префикс: слова, одинаковые в 2+ гипотезах подряд │
 │   • хвост (ещё не подтверждённое) — рисуем приглушённым             │
 │   • [v2] «вторая ступень»: GigaAM-v3 перераспознаёт окно и заменяет │
 └───────────────────────────┬─────────────────────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ 5. Оверлей субтитров (второй процесс или тот же, UI-поток)          │
 │   • прозрачное click-through окно поверх всех, без фокуса           │
 │   • 2–3 строки, крупный шрифт, обводка/подложка                     │
 │   • скрыто от демонстрации экрана (WDA_EXCLUDEFROMCAPTURE)          │
 │   • горячие клавиши, трей, история, экспорт .txt/.srt               │
 └─────────────────────────────────────────────────────────────────────┘
```

### 4.2 Разделение на процессы

Рекомендую **два процесса**: `audio+asr` (фоновый, стабильный, без UI) и `overlay` (окно), связанные локальным каналом (named pipe / shared memory). Причины:

- падение или перерисовка UI не роняет распознавание;
- оверлей можно перезапускать на лету, не теряя аудио;
- ASR-процессу можно поставить приоритет «ниже нормального», чтобы не мешать созвону.

Для v1 допустим и один процесс (проще отладка), разделение — тривиальное упражнение на этапе 3.

### 4.3 Ключевые технические решения

| Вопрос | Решение | Почему |
|---|---|---|
| Как «услышать то, что в наушниках» | WASAPI loopback; для изоляции от лишних звуков — process loopback на конкретное приложение | Штатный механизм Windows; process loopback требует Windows 10 сборки 20348+ и работает только в shared-режиме; DRM-звук не захватывается (по официальной документации Microsoft) |
| Частота и каналы | 16 кГц моно (движок сам срежет до 8 кГц для T-one) | Минимум вычислений; моно для речи достаточно |
| VAD | Silero VAD из состава sherpa-onnx | Не считать тишину, не порождать фантомный текст, определять конец реплики |
| Движок ASR | sherpa-onnx (C++/ONNX Runtime), биндинги C#, Rust, C | Один нативный процесс, без Python-рантайма; готовый Windows-релиз; все нужные модели в одном формате |
| Аппаратное ускорение | База — CPU (4–6 потоков). Опционально — эксперимент с DirectML | См. §8: встроенная графика на Windows ускоряет не всё и не бесплатно |
| Оверлей | Отдельное окно: `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST` | Прозрачность + клики «сквозь» + без значка в панели задач + не отбирает фокус |
| Скрытие от шаринга | `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` | Единственный штатный способ; границы надёжности — в §7 и §9 |

## 5. Как получить «слова по мере речи»

Три техники, которые комбинируются:

### 5.1 Нативный стриминг (основа v1)

T-one CTC обрабатывает поток чанками по 300 мс и держит акустическое состояние между чанками — это и есть потоковый режим (см. README T-one и документацию sherpa-onnx). Текст гипотезы обновляется с приходом очередного чанка; в конфигурации движка видно, что результат помечен `is_final: false` — то есть это промежуточная гипотеза, а не финал фразы.

Практическая задержка: 300 мс (накопление чанка) + 30–90 мс (инференс) + стабилизация. Ограничение: гипотеза может «дёргаться» в хвосте — лечится стабилизатором.

### 5.2 Стабилизатор текста (обязателен)

Приём известен как «local agreement»: сравниваем две последовательные гипотезы и подтверждаем только общий префикс; подтверждённый текст рисуем обычным цветом, хвост — приглушённым. Пользователь видит плавно растущую строку без мигания. Эффект: +0–300 мс задержки, зато читаемо.

### 5.3 Вторая ступень качества (v2, опционально)

Параллельно (или после паузы в 1.5–2 с) прогоняем окно последних 2–4 секунд через более точную модель (GigaAM-v3, `ctc`/`rnnt`/`e2e_*`) и **заменяем** хвост текста на её версию, уже с пунктуацией. Плюс: качество уровня «офлайн-расшифровки». Минус: текст в хвосте может видимо переписаться. Рекомендую включать эту опцию по умолчанию только для «неподтверждённой» части строки, а подтверждённую не трогать.

### 5.4 Бюджет задержки (целевой)

| Звено | Вклад |
|---|---|
| Буфер захвата WASAPI | 20–40 мс |
| Ресемплинг и накопление чанка 300 мс | 300 мс |
| Инференс чанка T-one (оценка для 4–6 потоков Zen4) | 30–90 мс |
| Стабилизатор (0 или 1 чанк) | 0–300 мс |
| Композитинг и вывод окна | ~16 мс |
| **Медиана «слово сказано → слово на экране»** | **≈ 0.4–0.75 с** |
| **P95** | **≈ 1.0–1.2 с** |

Оценка инференса — экстраполяция: в официальном примере sherpa-onnx модель T-one прогоняется с **одним потоком** с RTF 0.32 (2 с на 6.4 с аудио). На 4–6 потоках 8-ядерного Zen4 ожидаю RTF ~0.08–0.15, то есть 300-мс чанк считается за 25–45 мс. Это подлежит проверке на Этапе 0; если подтвердится, есть большой запас.

## 6. Язык и стек: варианты

Ядро распознавания в любом варианте — нативный C++ (sherpa-onnx через ONNX Runtime). Разница только в оболочке: захват звука, логика интерфейса, окно.

| Вариант | Плюсы | Минусы | Кому подходит |
|---|---|---|---|
| **C#/.NET 8** + NAudio (loopback) + sherpa-onnx (C#-биндинг) + WPF (`AllowsTransparency=true`, `WindowStyle=None`) + P/Invoke для `SetWindowDisplayAffinity` | Быстрее всех к рабочему прототипу; богатая работа с окнами; публикация NativeAOT даёт обычный exe без рантайма | Требуется .NET SDK при сборке; WPF-прозрачность чуть тяжелее нативного слоя (для маленького окна не критично) | **Рекомендую по умолчанию** — если нет предпочтения по языку |
| **Rust** + `wasapi` (есть `new_application_loopback_client`) + `windows` (WinAPI: стили окна, `SetWindowDisplayAffinity`, DirectWrite) + winit/egui (`with_transparent`, `content_protected`, `with_no_redirection_bitmap`) + `rubato` (ресемплинг) | Один компактный exe, минимальный оверхед, мгновенный старт, отличный контроль | Больше ручной работы с окнами и рисованием текста; дольше до первого результата | Если важны размер/скорость и есть готовность возиться |
| **C++/Win32** + Direct2D/DirectWrite + ApplicationLoopback | Максимальный контроль, ноль зависимостей | Заметно больший объём кода на ту же функциональность | Смысла мало: sherpa-onnx уже C++ |
| Python (только для этапа замеров) | Быстрее всего проверить модели и качество (pip-пакет sherpa-onnx) | GIL/паузы, тяжёлая упаковка, не тот уровень отзывчивости | **Этап 0–1**: замеры, не финальное приложение |

Промежуточный вывод: язык оболочки на задержку почти не влияет (упираемся в 300-мс чанк и в задержку модели), поэтому выбирать стоит по скорости разработки и поддерживаемости. Для v1 беру C#; перевод на Rust позже — это замена UI-слоя, не переписывание системы.

## 7. Оверлей: что именно нужно сделать

Обязательные свойства окна (WinAPI): `WS_EX_LAYERED` (прозрачность), `WS_EX_TRANSPARENT` (клики проходят сквозь), `WS_EX_TOOLWINDOW` (нет в панели задач/Alt-Tab), `WS_EX_NOACTIVATE` + показ через `SW_SHOWNOACTIVATE` (не забирает фокус у созвона), `WS_EX_TOPMOST` (поверх всех). В WPF это комбинация `AllowsTransparency`, `Topmost`, `ShowActivated=false` плюс вызовы `SetWindowLongPtr`/`SetWindowPos`.

1. **Скрытие от шаринга экрана**: `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` — доступно с Windows 10 2004. Важно: это не «безопасность», а удобство; в отчётах пользователей есть случаи на 24H2, когда скрытие заставляет захватчиков экрана получать лишние кадры, и нет публичной матрицы совместимости с Teams/Zoom/браузерами. Поэтому: (а) обязательно протестировать на её конкретном приложении созвона; (б) сделать горячую клавишу мгновенного скрытия/показа оверлея, чтобы это не было проблемой даже при сбое флага.
2. **Позиционирование**: нижняя треть монитора, per-monitor DPI awareness v2, привязка к выбранному монитору, перетаскивание с фиксацией позиции.
3. **Читаемость**: крупный рубленый шрифт (28–40 px и больше), толстая обводка или тень вокруг букв, опциональная полупрозрачная подложка-«пилюля» (скруглённый прямоугольник), 2–3 строки, перенос по словам. Палитра — с возможностью высокого контраста.
4. **Поведение текста**: подтверждённый текст — обычной яркостью, хвост — приглушённо; последняя фраза «залипает» на 1.5–3 с, потом тускнеет; по горячей клавише — окно истории за последние 30–60 с.
5. **Горячие клавиши**: сознательно не используются. Все действия доступны из меню значка в трее (включить/выключить субтитры, настройки, выход), чтобы программа не перехватывала системные сочетания.
6. **Эксплуатация**: иконка в трее, автозапуск при входе, восстановление после смены аудиоустройства (см. §9), один экземпляр приложения.

## 8. Аппаратное ускорение на её ноутбуке (7840HS + Radeon 780M)

Короткий ответ: **базовый путь — CPU, и его, скорее всего, хватит.**

- Модель T-one — всего 71 млн параметров; при RTF ~0.1 на 4–6 потоках она занимает менее одного ядра физически. Запас есть.
- **iGPU (780M) под Windows**: официальной поддержки ROCm для этого чипа (gfx1103) нет; практический путь — ONNX Runtime с DirectML-провайдером, но для потоковых моделей с состоянием и мелкими чанками накладные расходы на каждый вызов легко съедают выигрыш. Итог: эксперимент имеет смысл только если CPU окажется на пределе.
- **NPU (Ryzen AI первого поколения)**: пути ускорения существуют, но поддержка Whisper/ASR-моделей там ограничена и нацелена на новые поколения; практической ценности для этой задачи сейчас нет.
- **Vulkan** остаётся вариантом для семейства whisper.cpp (если когда-нибудь понадобится расшифровка записей), но не для нашей основной модели.
- Важный нюанс: во время созвона ноутбук уже занят (браузер/встреча), поэтому ASR-процессу ставим приоритет ниже нормального и ограничиваем 4–6 потоками — «не мешать созвону» важнее абсолютной скорости распознавания.

## 10. План работ

**Этап 0 — проверка на реальном ноутбуке (полвечера, без программирования).**
Прогнать готовый движок с моделью на записях её созвонов и посмотреть на качество и скорость своими глазами:

```powershell
# 1) скачать модель T-one для sherpa-onnx (Windows 10+ умеет tar из коробки)
curl.exe -L -o t-one.tar.bz2 https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-streaming-t-one-russian-2025-09-08.tar.bz2
tar -xjf t-one.tar.bz2

# 2) скачать релиз sherpa-onnx для Windows (в архиве — папка bin с exe)

# 3) прогнать пример из комплекта модели и посмотреть на RTF
.\bin\sherpa-onnx.exe --t-one-ctc-model=.\sherpa-onnx-streaming-t-one-russian-2025-09-08\model.onnx `
  --tokens=.\sherpa-onnx-streaming-t-one-russian-2025-09-08\tokens.txt `
  --num-threads=6 .\sherpa-onnx-streaming-t-one-russian-2025-09-08\0.wav

# 4) живая проверка с микрофоном (чтобы услышать потоковый вывод)
.\bin\sherpa-onnx-microphone.exe --t-one-ctc-model=.\sherpa-onnx-streaming-t-one-russian-2025-09-08\model.onnx `
  --tokens=.\sherpa-onnx-streaming-t-one-russian-2025-09-08\tokens.txt
```

Что фиксируем: RTF на 6 потоках; как часто обновляется текст (видно ли «по мере речи»); количество ошибок на 10–20 минутах реальных разговоров; поведение на её микрофоне. Параллельно — то же самое с GigaAM-v3 (пакет для sherpa-onnx) для сравнения по точности. Итог этапа — выбор основной модели и подтверждение запаса по CPU.

**Этап 1 — консольный прототип (1–2 дня).** Оболочка на C# (или Rust): захват loopback → чанки 300 мс → sherpa-onnx online → печать гипотез в консоль с временными метками. Замер сквозной задержки: включаем в наушниках щелчок/метроном, смотрим разницу «звук → слово на экране». Критерий: медиана ≤ 0.8 с.

**Этап 2 — оверлей (2–4 дня).** Прозрачное окно с §7, горячие клавиши, трей, настройки размеров и позиции, скрытие от захвата экрана. Проверка на её приложении созвона.

**Этап 3 — доведение (2–4 дня).** Стабилизатор текста, залипание фраз, история и экспорт, обработка смены устройств, автозапуск, упаковка в один exe, установщик, лог ошибок.

**Этап 4 (опционально).** Вторая ступень на GigaAM-v3, пунктуация и нормализация, словарь терминов, эксперимент с DirectML.

**Критерии приёмки (v1):**

- медиана «слово сказано → слово на экране» ≤ 0.8 с, P95 ≤ 1.5 с;
- загрузка ≤ 4–6 потоков CPU, заметного влияния на созвон нет;
- 8 часов работы без утечек памяти, без перезапуска;
- субтитры не видны при демонстрации экрана (проверено на её приложении);
- окно не перехватывает фокус и клики, отключается одной горячей клавишей;
- звук не покидает ноутбук; транскрипты по умолчанию не сохраняются.
